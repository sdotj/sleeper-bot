# SleepBot follow-up audit — September 8, 2026

Reviewed commit `5699355` and the five remediation commits following the previous audit. No application source was changed. All platform writes and model calls in the reproduction probes were mocked; no live league or Telegram actions were performed.

The original unauthenticated encoded-path bypass is closed. Partial auth configuration now fails startup, PostgreSQL certificate verification defaults to enabled, login uses bounded asynchronous hashing, malformed write payloads receive domain validation, and production dependency advisories have been eliminated in the current npm scan. However, several findings marked fixed are only partially addressed. The remaining high-priority issues concern approval policy and write integrity, including failures in a single process.

**Actionable findings, ordered by impact**

1. **High — chat still executes proposals in global auto mode.** Reproduced through the actual `dispatchTool → SleepBotOperations → ActionPipeline` chain with a mocked adapter: calling only `propose_add_drop` produced one platform dispatch and `status: executed`. Removing `execute_action` from the chat tool catalog closes the manual-mode path, but [pipeline.ts:92](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/actions/pipeline.ts:92>) still auto-executes proposals. This contradicts the new unconditional human-gating guarantee and the tool descriptions. Global auto also permits warned actions while the scheduled agent's auto policy does not. Make proposal creation incapable of dispatching, or explicitly enforce a draft-only capability for chat independent of global settings. Add a regression test using the real dispatcher and pipeline with `mode: auto`; asserting only that `execute_action` is absent misses this path. Previous finding #3 remains partially open.

2. **High — Telegram's new lock ends before the durable action is consumed.** [notifier.ts:141](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/notify/notifier.ts:141>) clears `inFlight` before awaiting outbox deletion. Reproduction delayed `store.delete`, then delivered a second callback: the same notifier instance performed the same action **twice**. This does not require multiple instances. The record is also fetched before claiming, which makes stale reads another consideration. Hold the claim through the entire state transition, and use an atomic durable claim for cross-instance safety. Tests should delay persistence as well as the platform call. Previous #4 remains open for Telegram.

3. **High — a storage failure after a successful send makes retries resend.** [pipeline.ts:142](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/actions/pipeline.ts:142>) changes the status of its local object, writes an audit event, then deletes the pending record; it does not durably record an execution claim/result on that record. Using a snapshot-returning store to model PostgreSQL, I injected failure while writing the executed audit event. The first send succeeded, the stored action remained `pending`, and retrying caused a second send. The new in-memory lock has already been released by then. Introduce durable `executing`, `executed`, `failed`, and `unknown` states with a stable execution ID. Reconcile ambiguous results instead of automatically permitting resend. The current single-instance guidance does not address this failure. Two pipeline/notifier instances also still have independent locks, so multi-writer operation remains unsupported. Previous #4 is mitigated only for overlapping `execute` calls on one pipeline before failure.

4. **High — refreshed settings do not revoke an already-selected agent auto policy.** [start.ts:106](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/agent/start.ts:106>) selects enabled leagues and captures autonomy before [agentRunner.ts:34](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/agent/agentRunner.ts:34>) refreshes configuration. The runner continues using its old `autonomy` argument and never checks enabled status again before dispatch. A mocked refresh that disabled the league still resulted in one auto write. Changes made during the potentially long reasoning phase have the same problem. Refresh failures are swallowed, which further favors stale authority. Reload and validate the current enabled/autonomy policy before selecting work and immediately before every automated write; fail closed on refresh failure. Telegram and MCP execution also bypass the facade's new refresh hook. This is a correctness gap in the mitigation for previous #14.

5. **High — changing a configured league can redirect an existing pending action.** [ProposedAction.ts:14](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/actions/ProposedAction.ts:14>) stores the mutable league label, not the immutable platform league/account identity or config version approved by the user. At execution, [pipeline.ts:111](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/actions/pipeline.ts:111>) resolves the current adapter for that label. Reproduction proposed against an old adapter target, remapped the label, and observed dispatch to the new target. If the new league contains compatible player/roster IDs and the credentials authorize it, an old approval can affect a different league. Bind proposals to platform, league, actor/roster, and relevant policy/config revision; invalidate or require reapproval when those change. Apply the same rule to Telegram outbox records. No live cross-league write was attempted.

6. **Medium — concurrent chat turns still overwrite each other.** [session.ts:77](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/chat/session.ts:77>) adds a second read, but that read and the final write are still separate operations. Two concurrent turns using independent document snapshots left **two messages instead of four**, just as in the first audit. This can occur with one Node process because database I/O yields between operations. Re-reading narrows a race window; it does not serialize or atomically append. Use append-only message rows with transactional sequencing, optimistic version checks, or a per-conversation queue for explicitly single-process operation. A deleted conversation can also be resurrected by the `?? convo` fallback. Previous #13 should not be marked fixed.

7. **Medium — version stamps can collide and miss configuration updates.** [context.ts:120](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/core/context.ts:120>) derives a supposedly monotonic version independently in each process from `Date.now()` and local state. Two contexts writing in the same millisecond produced the same version. After B saved newer configuration, A's `refresh()` did nothing: storage contained B, while A still used A. I reproduced this with the actual context builder and a fixed clock. Config/token writes and version updates are also separate writes, so failure between them can leave undetectable changes. Use a database-generated revision or transactional update/CAS; track revision equality rather than assuming distributed wall clocks provide a global ordering. The mitigation also does not cover MCP tools that call context collaborators directly.

8. **Medium — the replacement GUI approval workflow does not exist.** [chatLoop.ts:35](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/chat/chatLoop.ts:35>) now instructs chat to tell users to click Send in a pending-actions list. The React application has no pending-action list, no execute API client method, and no approval button; [Audit.tsx:13](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/web/src/features/audit/Audit.tsx:13>) only renders event summaries. In manual mode, users can create drafts in chat but cannot approve them in the web app as instructed. Implement authenticated proposal review and approval, with exact payload/league details, current warnings, and cancellation, and align the model instructions with that actual workflow. The MCP tool and raw HTTP execution route remain available, but neither supplies the promised GUI.

9. **Medium — failed automatic writes still report `failed: 0`.** [agentRunner.ts:133](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/agent/agentRunner.ts:133>) catches platform execution failures internally, sends a notification, and returns normally. The caller then increments `routed`. Reproduction with a throwing `perform` returned `{recommended:1,routed:1,failed:0}`. `sweepAll` also continues to total recommendations rather than delivered proposals or successful executions. If `perform` returns a rejected action after a second rule check, the current code can still emit an Auto-executed notification without checking its status. Return typed routing outcomes and aggregate proposed/executed/rejected/failed separately. Previous #17 is only partly addressed.

10. **Medium — deployment instructions still allow an open production API and multiple writers.** The [Fly.io deploy example](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/docs/deploy.md:93>) sets service credentials but none of the login variables or `SLEEPBOT_REQUIRE_AUTH`; all-unset auth remains allowed, and the Docker runtime binds to `0.0.0.0`. Following that example alone exposes the API. Later prose still describes multiple API instances behind a load balancer as supported, while action locks are instance-local and the Cloud Run example does not enforce a single-writer limit. Make complete deployment examples safe on their own: include required auth/rules settings and enforce the current writer constraint. Explain how overlapping revisions and API/MCP processes are handled, rather than relying on a comment that says there is one writer. This is deployment guidance exposure, not a newly discovered bypass of the configured auth gate.

**Other remaining gaps and structural assessment**

- The shared-core/adapters design is still appropriate. The most useful refactor is one operation boundary and one action lifecycle, not a larger framework or a service split. `SleepBotOperations` now performs refreshes, while MCP tools and Telegram callbacks bypass it; that duplication is causing observable safety differences.
- The write schemas are a substantive improvement, but they validate request shape rather than roster ownership, current roster contents, remaining FAAB, or supported platform capabilities. `execute` does not re-parse persisted legacy payloads. Add execution preconditions to a shared service; avoid assuming the rules engine already performs the roster revalidation described in comments.
- Telegram now correctly rejects callbacks without a message and rejects approval/override mode mismatches. However it still sends buttons before saving the outbox record, deletes records on failed execution/unknown verbs, has no proposal expiry, and does not audit denials. Changing the HTTP webhook to return 500 does not help failures swallowed inside the notifier. Unknown external write outcomes need reconciliation, not a blanket safe-to-retry claim.
- Graceful shutdown stops timers/polling but does not await an active background sweep or callback before closing the database pool and exiting. HTTP draining covers request-bound work, not autonomous timer work. Track active background promises and drain them with a bounded deadline. This interacts with the post-send persistence failure in finding 3.
- Frontend league remounting and request tokens address the main prior races. A smaller regression remains in `ChatPane`: clicking New chat during `openConvo` increments the view token but does not reset `loadingThread`; the stale request's finally block will no longer clear it. Sending is also allowed while a thread is loading, so a delayed history response can replace a newly displayed turn. Reset loading state on navigation and disable/sequence sends during initial thread loading. These UI cases were inspected in source, not browser-reproduced.
- Chat/model calls remain unbounded across concurrent HTTP requests. Login limits do not limit paid model usage. Add request concurrency, budget limits, and cancellation. API read/query parameters and draft-chat history still rely primarily on casts. The existing model-loop count only caps an individual request.
- Generic key/value storage still fetches entire collections, and history listing fetches all messages before producing summaries. These are accepted personal-scale constraints, but a repository layer with transactions, pagination, and append-only history is now justified by demonstrated correctness problems as well as scale.
- The new value-provider retry and ESPN TTL changes address their targeted failures. Sleeper's cached self-user lookup still converts a transient failure to a permanently cached null, and several Sleeper/Telegram fetches lack explicit deadlines. Provider health and data age should be visible.
- Tool descriptions and the README still contain stale capability/approval claims. Explicit adapter capability flags, shared domain schemas, a split settings component, and a shared chat request controller remain worthwhile. A generated operation catalog is optional; consistently enforcing domain authorization is not.
- No tracked CI workflow was found. The existing unit tests predominantly use in-memory references and sequential success cases. Add deterministic storage-delay/failure tests, concurrent independent snapshots, a disposable PostgreSQL integration run, and frontend approval/navigation tests. The second read in the chat fix illustrates why a sequential regression test can pass while the original bug remains.

- Backend and frontend TypeScript checks passed; Vite production build passed.
- Direct auth probes now return 401 for unauthenticated `/api/leagues`, `/%61pi/leagues`, encoded config PUT, encoded execute POST, and `/a%70i/leagues`; the double-encoded nonexistent route returns 404.

Fix the approval loophole and durable write state first. Then bind proposals to immutable targets/current policy and make chat history append atomic. A unified action repository with explicit states and failure-injection tests would address more of the remaining risk than additional per-process flags or last-minute re-reads.
