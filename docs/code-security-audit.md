# SleepBot audit — September 7, 2026

SleepBot has a useful shared-core architecture, but the current HTTP authentication bypass is a release blocker for a publicly reachable deployment. Several independent problems can cause unintended, duplicated, or falsely reported league writes. Address these before expanding automation or running multiple instances.

This was a source review, local test run, dependency audit, and targeted reproduction exercise. Application source was not modified. All write-operation reproductions used mocks; no Sleeper, ESPN, Telegram, or Anthropic actions were sent. Deployment configuration, infrastructure controls, live credentials, and real platform protocols were not verified. Severity describes this application's impact, rather than copying dependency advisory scores.

**Security and write integrity**

1. **Critical — encoded paths bypass authentication (reproduced).** [registerAuth.ts:70](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/gate/registerAuth.ts:70>) classifies public requests using the raw URL and exempts anything not beginning with `/api/`. Fastify matches percent-decoded paths. With complete dummy login configuration, unauthenticated `GET /api/leagues` returned 401, while `GET /%61pi/leagues` returned 200 with fixture data. Mocked `PUT /%61pi/config` and `POST /%61pi/actions/fixture/execute` also reached their handlers and returned 200. The same guard protects chat, secrets management, conversations, and pending actions, so impact extends beyond reading league data. A caller that can reach the service can bypass its login gate; any actual league write still depends on available platform credentials and platform acceptance. Fix by attaching authentication to a protected Fastify route scope or explicit route metadata, with narrowly declared public routes. Do not base authorization on raw-path string prefixes. Add regression coverage for encoded paths and every HTTP method. Until fixed, restrict access through an independently enforced network or identity boundary.

2. **High — partial authentication configuration opens the API (reproduced).** [registerAuth.ts:23](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/gate/registerAuth.ts:23>) logs and continues without auth if any one credential setting is missing. Removing only the dummy JWT secret yielded an unauthenticated 200 for `/api/leagues`. The container binds to all interfaces, making a deployment-secret omission consequential. Reject partial configuration at startup; require an explicit local-development opt-out to run without auth, and validate signing-key strength and password-hash format before listening.

3. **High — chat approval is a prompt instruction, not a server-enforced boundary (source confirmed; no live prompt-injection attempt).** [tools.ts:45](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/chat/tools.ts:45>) exposes both proposing and executing actions to the model; `dispatchTool` invokes execution using only an action ID. [chatLoop.ts:105](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/chat/chatLoop.ts:105>) runs returned tool calls automatically. A model can propose and execute in the same turn without a separately verified human approval. League data and web results enter its context, and model-written memory is later appended to the system prompt. The draft-chat route additionally accepts client-supplied history. Fix by requiring an authenticated, server-recorded approval bound to the exact immutable proposal, and keeping approval creation outside model-callable tools. Make draft chat read-only unless writes are explicitly needed. Treat retrieved text and stored memory as untrusted data. This follows [OWASP's guidance on tool permissions and human approval](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html).

4. **High — a single pending action can execute twice (reproduced).** [pipeline.ts:84](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/actions/pipeline.ts:84>) reads a pending document, dispatches the external write, then removes it. Two concurrent calls for the same ID produced **two mock platform writes**. [notifier.ts:102](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/notify/notifier.ts:102>) uses the same read/perform/delete pattern. Retries after an external success but a persistence failure are also ambiguous. PostgreSQL upserts do not make this multi-step workflow atomic. Introduce a durable action state machine with atomic claiming, stable execution IDs, and explicit reconciliation for uncertain platform outcomes. Do not blindly retry a write after a timeout. Add concurrent approval and post-dispatch storage-failure tests. Scheduled sweeps also need per-league locking and recommendation deduplication.

5. **High — production can silently lose configured guardrails (source confirmed; read-error fallback reproduced).** [.dockerignore:11](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/.dockerignore:11>) excludes `config/rules.json`, while [schema.ts:47](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/rules/schema.ts:47>) only loads rules from a file and returns empty protection/warning lists on **any** read error. Passing a directory as the configured rules path reproduced the empty-rule fallback. The documented container setup has no rules JSON environment seed or settings-store rules path. Unless a rules file is separately mounted, locally configured protections disappear. Per-league agent `auto` mode is independent of the returned global `manual` default, so automated writes can still run with empty guardrails. Persist/version rules with configuration, support a documented deployment seed or required mount, and fail startup on unreadable explicitly configured rules. Only distinguish an intentionally absent optional default file from corruption or permission errors.

6. **High — PostgreSQL TLS disables server certificate verification (source confirmed).** [postgresStore.ts:43](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/audit/postgresStore.ts:43>) sets `rejectUnauthorized: false` for remote database connections, including when `DATABASE_SSL=true`. The connection is encrypted but the application does not verify the server certificate. A network attacker capable of interception could impersonate the database endpoint. Use certificate verification with the provider's CA where needed; do not silently downgrade. The driver supports normal TLS configuration through its `ssl` option: [node-postgres SSL documentation](https://node-postgres.com/features/ssl).

7. **High — public login performs unthrottled synchronous password hashing (source confirmed).** [registerAuth.ts:37](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/gate/registerAuth.ts:37>) invokes [credentials.ts:29](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/gate/credentials.ts:29>) for every login request, including unknown users. `scryptSync` blocks the event loop, and no application rate limiter or concurrency bound is registered. Repeated login attempts can monopolize the process. Use asynchronous scrypt with bounded concurrency, rate-limit login attempts, and bound request fields. Chat and manual sweeps also need concurrency and spending limits; their tool-loop limits only constrain an individual request. Any upstream rate limiting was outside this audit's scope.

8. **High — unsuccessful or malformed platform responses can be reported as executed (reproduced).** [sleeperWriteClient.ts:149](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/adapters/sleeper/sleeperWriteClient.ts:149>) always returns `ok: true`, even if the mutation result is absent or null. Its GraphQL helper also does not reject non-success HTTP status codes unless the body contains a recognized error. A mocked `{data:{create_free_agent:null}}` response returned success with status `unknown`. [pipeline.ts:113](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/actions/pipeline.ts:113>) marks every resolved result executed without checking `result.ok`. Validate HTTP status and the mutation response schema, recognize accepted/rejected platform states, and distinguish submitted, completed, failed, and unknown outcomes. Never remove a pending action solely because a transport promise resolved.

9. **Medium — proposal responses falsely claim that already-executed writes are drafts (reproduced).** [operations.ts:16](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/core/operations.ts:16>) handles rejected actions and treats all other states as pending. In global auto mode, a proposal returned `status: executed` together with `Proposed as a DRAFT — nothing has been sent.` Tool descriptions likewise promise that proposing never sends. Global auto mode also executes warned actions, whereas agent auto mode waits for approval on warnings. Fix the response formatter with exhaustive state handling and establish one explicit policy for proposal versus execution. Update tool descriptions to match actual behavior, ideally making proposal creation side-effect-free with respect to platform writes.

10. **Medium — HTTP and model tools lack shared runtime validation (reproduced at the route boundary).** [server.ts:139](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/api/server.ts:139>) casts bodies to TypeScript interfaces; [chat/tools.ts:63](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/chat/tools.ts:63>) and [agentTools.ts:56](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/agent/agentTools.ts:56>) cast model inputs to `any`. These casts do not validate data. A negative fractional roster ID, numeric player ID, and negative FAAB bid passed through the API to a mocked operation with a 200 response. This demonstrates missing boundary validation, not platform acceptance. Define shared discriminated Zod schemas and validate at the domain entry point as well as transports. Enforce positive integer IDs where appropriate, budget limits, nonempty/nonoverlapping trades, and the user's roster identity. Current rule evaluation checks protected players and values; it does not actually re-fetch roster ownership or affordability despite the revalidation comment.

11. **Medium — Telegram callback authorization and lifecycle are incomplete (handler behavior reproduced).** [notifier.ts:132](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/notify/notifier.ts:132>) checks the chat only when `message` exists; missing-message callbacks continue. The handler ignores the stored proposal mode and accepts `ovr:` for an ordinary approval proposal. A synthetic missing-message callback executed a mock action with `override: true` despite the stored mode being `approve`. This is not a demonstrated unauthenticated HTTP attack: the webhook has its own secret, and polling receives Telegram responses. Require the expected chat/message and allowed actor, validate callback mode against stored state, and reject unexpected verbs. Persist before sending buttons, retain recoverable failures, expire stale proposals, and audit approvals, denials, and overrides. Currently failed and unknown callbacks delete the outbox record; denials are not recorded in the audit log.

**Persistence and application correctness**

12. **Medium — a damaged local store can be silently overwritten (reproduced).** [store.ts:37](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/audit/store.ts:37>) treats malformed JSON and all read failures as an empty database. A truncated test file was replaced with only the next new record, losing its prior contents. Writes rewrite the destination directly rather than using atomic replacement. The rejected `writeChain` also prevents later writes from attempting recovery after one persistence failure. Handle only ENOENT as a new store; fail clearly on corruption, preserve the damaged file, and use atomic replacement with a recovery strategy. For stronger local persistence, consider SQLite. The current JSON store should not be shared by separately running MCP/API processes.

13. **Medium — concurrent chat turns overwrite each other in PostgreSQL semantics (reproduced with independent document snapshots).** [session.ts:46](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/chat/session.ts:46>) loads a conversation, performs a long model call, appends a turn, then overwrites the document. Two concurrent turns left **two stored messages instead of four** in a snapshot-returning test store. The built-in memory store returns shared object references, which can hide this production behavior in tests. Use append-only message records and per-conversation sequencing or optimistic version checks. Protect rename/delete against concurrent turns and decide how interrupted turns are recovered.

14. **Medium — settings and credentials remain stale in other instances (source confirmed).** [context.ts:119](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/core/context.ts:119>) maintains local adapter, config, and session state. `saveConfig` and `setSleeperToken` update the shared store and the handling process, but other processes do not refresh automatically. Behind a load balancer, one instance can use changed league settings or a replacement token while another uses old values. Enabling the first agent-enabled league also needs a restart because [start.ts:29](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/agent/start.ts:29>) returns before starting the manager when none were enabled at boot. Add versioned refresh/invalidation or explicitly support one active manager instance until coordination exists. PostgreSQL persistence alone does not make horizontal scaling safe.

15. **Medium — caches can remain failed or stale until restart (partly reproduced).** [sleeperRank.ts:51](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/value/sleeperRank.ts:51>) permanently retains the first rejected build promise. Two attempts after a simulated transient first-load failure invoked the loader only once. [ktc.ts:60](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/value/ktc.ts:60>) has the same pattern. Successful value indexes also never refresh. [espnClient.ts:144](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/adapters/espn/espnClient.ts:144>) caches ownership and injury data indefinitely even though it drives trending and player views. Clear rejected initialization promises, use explicit TTLs or snapshot versions, expose data age, and add request deadlines. Sleeper, ESPN, and Telegram fetches currently lack application-level abort deadlines.

16. **Medium — asynchronous frontend state can mix leagues or conversations (source confirmed).** [DraftView.tsx:10](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/web/src/features/draft/DraftView.tsx:10>) retains `draftId`, manual draft ID, and roster ID when its `leagueId` prop changes; [App.tsx:153](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/web/src/App.tsx:153>) does not key the view by league. [api.ts:136](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/web/src/lib/api.ts:136>) keeps previous data across all dependency changes, including a different league, not just a refresh. A prior league's draft can remain active under the new selection. [ChatPane.tsx:56](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/web/src/features/chat/ChatPane.tsx:56>) allows conversation changes during requests without checking which conversation a response belongs to; an old response can replace or append to the visible new thread. Reset or key league-scoped state and tie every response to its request/conversation identity. Preserve previous data only for refreshes of the same resource. These UI races were inspected in source, not exercised in a browser.

17. **Medium — failures and growing data sets are poorly bounded (source confirmed).** [agentRunner.ts:36](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/agent/agentRunner.ts:36>) swallows routing failures and still returns the number of recommendations as if processing succeeded. The webhook also swallows handling failures and returns success, preventing delivery retries. [postgresStore.ts:84](</Users/samjenkins/Desktop/Personal Projects/sleep-bot/src/audit/postgresStore.ts:84>) fetches whole collections; audit and conversation listing then filter/sort in memory, and conversation summaries load all message bodies first. Add structured failure outcomes and logs, request IDs, actionable health/readiness checks, pagination, database-side filtering, retention, and queryable summary/message tables. Bound scheduled work and implement graceful shutdown of polling, the HTTP server, and the database pool.

**Dependencies**

Live `npm audit` completed for both lockfiles. The root dependency tree reported **8 affected package entries: 3 critical, 1 high, 4 moderate**. The frontend tree reported **2: 1 high, 1 moderate**. These are package entries, including transitive propagation, not ten independently exploitable application flaws.

- Root: `@fastify/jwt` 9.1.0 / `fast-jwt` 5.0.6; `qs` 6.15.3; and development dependencies Vitest 2.1.9, Vite 5.4.21, esbuild, vite-node, and @vitest/mocker.
- Frontend: Vite 5.4.21 and its esbuild dependency. The production Docker image serves built assets rather than a Vite development server.
- The [critical fast-jwt async-key advisory](https://github.com/nearform/fast-jwt/security/advisories/GHSA-gmvf-9v4p-v8jc) requires an asynchronous key resolver returning an empty secret. SleepBot uses a static nonempty secret when enabled, so that particular advisory is not evidence of a second exploitable login bypass here.
- The [critical Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp) requires its UI server to be listening. The repository uses `vitest run`; production omits development dependencies. The reported qs dependency is under the MCP SDK's Express dependency, while the current server entry points use stdio and Fastify; reachability of the vulnerable parser was not established.

Upgrade supported dependency lines, rerun behavior tests, and evaluate each advisory's preconditions. Do not blindly apply `npm audit fix --force`: suggested direct-package fixes include major-version changes. **Structure, reuse, and maintainability**

- Keep the shared core and adapters. There is no evidence this project needs microservices. The largest complexity reduction would come from making existing boundaries consistent.
- Establish one validated operation catalog. MCP Zod schemas, chat JSON schemas, agent schemas/dispatch, HTTP casts, and browser DTOs currently duplicate contracts. MCP tools also frequently call `AppContext` collaborators directly, rather than the operations facade. Generate transport schemas from domain schemas and route consumers through the same validated operations. This directly addresses finding 10.
- Separate platform capabilities. `EspnAdapter` implements `WriteableLeagueAdapter` but throws for writes and drafts. Expose read/write/draft capabilities explicitly so UI and AI tools can omit unsupported operations; distinguish unsupported writes from expired authentication.
- Move generic persistence out of `audit`. The `Store` abstraction now supports config, secrets, history, memory, pending actions, and notifications. An infrastructure/storage module plus purpose-specific repositories would make ownership clearer and provide a place for transactions, pagination, and optimistic locking.
- Consolidate action lifecycles. MCP/HTTP pending actions and Telegram's outbox have separate approval representations; `perform` creates a different action ID from the agent proposal. Preserve one action identity and state history across proposal, approval, dispatch, and result.
- Split the 553-line settings file along its existing panel boundaries. Extract shared request hooks and cancellation behavior from the two chat implementations. Focus on eliminating duplicated state-handling logic rather than creating more tiny wrappers.
- Add automated gates that check the frontend and tests as well as backend production sources. The backend TypeScript config excludes test files; Vite builds do not typecheck. No tracked GitHub Actions workflow was found. Add CI with backend/frontend typechecks, unit tests, a real disposable PostgreSQL integration run, frontend interaction tests, and dependency scans. Prioritize the concrete regression cases above instead of chasing a coverage percentage.
- Update stale documentation. The README still presents ESPN as future work. Deployment prose overstates statelessness and safe multi-instance scaling. Tool comments promise proposals never send, and comments describe roster revalidation that is not performed. Cairn's 21 warnings all concern absent declared architecture contracts; adding real behavioral contracts around auth, action states, and storage would be more useful than cosmetic reorganization.

Additional hardening: use a non-root Docker runtime user; encode path parameters in the browser API client; avoid storing literal ESPN cookies in the generic plaintext config returned by `getConfig`; tighten session lifetime/revocation and browser security headers. The localStorage token is an exposure amplifier if an XSS bug appears, but this review did not identify a concrete HTML injection sink. The existing AES-256-GCM secret encryption, scrypt password hashing, parameterized SQL values, server-side API credentials, and injectable adapter seams are good foundations.

**Verification and order of work**

- Existing suite: **112 passed**, one PostgreSQL integration test skipped because no database was configured.
- Backend TypeScript checking: passed.
- Frontend TypeScript checking and production Vite build: passed.
- Cairn scan: zero errors, 21 contract warnings; hook gate passed.
- Local probes reproduced encoded read/write auth bypasses, fail-open partial auth, duplicate execution, malformed payload forwarding, false draft and platform-success messages, lost local data, unreadable-rule fallback, missing-chat/mode callback acceptance, poisoned ranking initialization, and concurrent chat lost updates.

Fix authorization first, then action approval/idempotency and production guardrails, then TLS/login resource controls and response validation. Follow with persistence and frontend correctness. Shared schemas, a unified action repository, and regression tests should accompany these fixes; a large architectural rewrite would delay the important work.
